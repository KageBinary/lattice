# M6.1d — Laws that are fast and that can be looked at

Governing specification: `docs/spec/project-lattice-spec-v0.1.md`, §8.3, NFR-001, NFR-007,
§17.2, and §24.1's dependency policy ("cacheable and inspectable in debug builds").
Roadmap row: `docs/roadmap.md:694`.

## 1. Summary

M6.1b made user laws run, and they cost 3.7–4.8× the built-in Lennard-Jones because the
interpreter dispatches one `match` per operation per pair (`crates/lattice-expr/src/lib.rs:198`,
`:375`). Spec §8.3 says users should get expressiveness *"without forcing every custom law
through a slow interpreter"*. When a law produces a NaN, the run halts with
`StopReason::NonFinite` (`crates/lattice-runtime/src/lib.rs:163`), which names the observation
but not the law or the sub-expression responsible. NFR-007 says to expose instability, and
the user can't act on "`kinetic_energy` became non-finite". There's also no way to see what a
law compiled to. M6.1d adds three things: a batched interpreter that is bit-identical to the
scalar one, tracing from a non-finite value back to the source span that produced it, and
`lattice inspect expr`, which prints a compiled law next to its source.

## 2. Goals and non-goals

Goals:
- G1. `Program::eval_batch` evaluates `LANES` independent sets of inputs in one pass. Every
  lane gets the same bits that `Program::eval` gives it, including NaN payload sign where
  Rust's `f64` operations define it, `-0.0`, infinities and subnormals.
- G2. The particle domain's pair and body loops use the batched path. Forces, energies and
  the virial don't change by a single bit, and neither does the order of force accumulation.
  The existing bit-identity validation cases (`lattice validate --filter laws`, and the
  thread-count identity case) pass unchanged.
- G3. Every operation in a `Program` carries an `Origin`, the byte range of the source
  expression that produced it. Derivative operations inherit the origin of the operation
  they differentiate.
- G4. When a run halts as non-finite and a user law is responsible, the message names the
  law, the first operation that went non-finite, its source span (rendered as a normal
  diagnostic with the caret under the sub-expression), and the operand values that went in.
  This covers particle laws and rate laws.
- G5. `lattice inspect expr <file.lattice> [law]` prints each law's kind, input layout,
  parameters, operation listing with registers and source, outputs, derivative program size,
  register budget, and fingerprint.

Non-goals:
- Native code generation or JIT. §8.3 allows it, but this is an interpreter improvement.
  WGSL lowering is M6.3.
- Batching the chemistry kinetics across cells. Cells take different adaptive sub-steps
  (`crates/lattice-domain-chemistry/src/kinetics.rs`), so lanes would diverge. Rate laws get
  tracing (G4) but keep scalar evaluation. Revisit if a rate-law benchmark shows it matters.
- Any change to what the builder does to a program. It still never reassociates, fuses or
  reciprocates (`crates/lattice-expr/src/lib.rs:12-19`).
- SIMD intrinsics or `unsafe`. Autovectorization of the inner lane loop is welcome but not
  required, and the crate stays std-only.

## 4. Design

### 4.1 Origins (G3)

```rust
/// Byte range in the law's source file; lattice-expr stays independent of lattice-syntax.
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct Origin { pub start: u32, pub end: u32 }

impl Builder {
    /// Set the origin given to operations pushed from now on.
    pub fn at(&mut self, origin: Option<Origin>);
}
impl Program {
    pub fn origin(&self, reg: Reg) -> Option<Origin>;
}
```

- `Program` gains `origins: Vec<Option<Origin>>`, parallel to `ops`.
- `PartialEq` becomes a manual impl that ignores origins, and `fingerprint` ignores them too.
  Two laws that compute the same thing are the same program wherever they were written.
- When CSE returns an existing register, the existing op keeps its first origin.
- A folded constant keeps the origin of the expression it came from.
- `gradient` gives every tangent op the origin of its primal op.
- `Lowering::expr` calls `b.at(Some(span))` before it pushes each node's ops. The span is the
  sub-expression's span, not the whole law's.

### 4.2 Batched evaluation (G1)

```rust
pub const LANES: usize = 8;

impl Program {
    /// inputs[k * LANES + l] is input k of lane l; out[o * LANES + l] likewise.
    /// regs.len() >= ops.len() * LANES. Lanes >= `active` are computed but ignored.
    pub fn eval_batch(&self, active: usize, inputs: &[f64], params: &[f64],
                      regs: &mut [f64], out: &mut [f64]);
}
```

- The op loop is outside and the lane loop inside, so one `match` covers `LANES` values.
  Each arm runs the exact scalar expression `apply` uses, for example
  `regs[r*L+l] = regs[a*L+l] + regs[b*L+l]`. The function is the same and the operands
  are the same, so the bits are the same. That's the whole bit-identity argument, and the
  tests below check it.
- `LANES = 8` makes the register file at most `512 × 8 × 8 B = 32 KiB`, which fits L1 and a
  stack array. The domain owns a `Box<[f64]>` scratch, allocated once at construction and
  never in the step (NFR-001).
- Lanes past `active` are filled with the last active lane's inputs, so they cannot raise
  anything unusual. Their outputs are discarded.
- `Select` stays per lane. Both arms are already computed because the program is SSA, so
  there is no divergence.

### 4.3 The particle loops (G2)

`for_each_pair_force` gathers pairs from `NeighborList::for_each_pair` into a batch of
`LANES` entries `(i, j, dx, dy, r)` and their input rows. When the batch is full, and once
more at the end, it evaluates and then calls `visit` for each lane **in gather order**. The
visit sequence is the scalar sequence, so accumulation into `force_x/force_y`, the energy
sum and the virial sum come out bit-identical. Member-dependent truncation runs a second
batch with `R` set to the cutoff, as it does today. `for_each_body_force` batches over
particle indices in the same way.

The scalar `eval` stays. Compile-time sampling uses it, and it is the reference the batched
path is tested against.

### 4.4 Tracing non-finite values (G4)

```rust
pub struct NonFiniteAt { pub reg: Reg, pub op: Op, pub origin: Option<Origin>,
                         pub operands: Vec<f64>, pub value: f64 }
impl Program {
    /// Scalar evaluation that stops at the first op whose result is non-finite while
    /// all its operands were finite. Allocates; diagnostic path only.
    pub fn trace(&self, inputs: &[f64], params: &[f64]) -> Option<NonFiniteAt>;
}
```

An op whose operands were already non-finite is skipped because it only propagated the
value. An input that is already non-finite is reported as one, with its layout name, and no
op is blamed.

**How the failing state is reached (O1, decided 2026-11-03: replay).** Runs are
bit-reproducible. When a run halts as `NonFinite` at step N, the CLI rebuilds the model,
steps to N−1, and runs step N with a `trace` hook enabled in each `ForceLaw`/rate law.
Nothing is retained during the step, so the hot path costs nothing. The cost is one extra
run, and only on failure. The hook is a new defaulted trait method:

```rust
fn explain_non_finite(&self, store: &ParticleStore, ctx: &ForceContext<'_>)
    -> Option<LawFault>;  // LawFault { law: String, pair: Option<(usize, usize)>, at: NonFiniteAt }
```

`RateExpression` gains the equivalent per cell. The CLI turns a `LawFault` into a
`Diagnostic` (code `E0950`, "law produced a non-finite value") whose primary span is the
origin. It notes the operand values, the pair or cell, and the step, and prints it under
the existing `HALTED:` line.

### 4.5 `lattice inspect expr` (G5)

`lattice inspect expr <file> [law]` compiles the file with the normal pipeline and prints,
for each law or only the named one:

```
law lj: pair potential, 14 inputs (dx dy r a.px … b.charge), 2 params (epsilon sigma)
  r0   input r                        | r
  r3   div   r2 r0                    | sigma / r
  …
  outputs: U = r11, dU/dr = r23     derivative: 24 ops    registers 24 / 512
  fingerprint 0x…
```

Each row shows the register, the op and its operands, and then the source text of its
origin, cut to one line. A law with a use site also lists the bound parameter values for
each use. An unknown law name is an error that lists the names that exist. A file that
fails to compile prints its diagnostics and exits non-zero.

## 5. Alternatives considered

- **Closure-threaded code** (compiling each op into a boxed closure). It removes the
  `match` but adds an indirect call per op per pair. It's no faster in the scalar case and
  it can't amortize across lanes. Rejected.
- **Register-to-register bytecode with superinstructions** (fusing `Mul`+`Add` patterns into
  one dispatch). A fused dispatch can still compute exactly, but it multiplies the op set and
  the derivative transform, and batching gets most of the win with no new ops. Deferred.
- **Checked evaluation in the hot path** (testing `is_finite` on every op every step). It
  costs every run in order to help failing ones. Rejected in favour of replay or the
  snapshot option.
- **`LANES = 4` or 16.** Four halves the amortization. Sixteen gives a 64 KiB register file
  and spills L1 on a 512-op law. Eight is the middle, and it's a `const`, so the benchmark
  can confirm it.

## 6. Risks and open questions

- **O1 (decided): how tracing reaches the failing state.** (a) Replay to N−1, as
  recommended in §4.4: zero hot-path cost, exact because runs are deterministic, but the
  replay doubles the time to failure. (b) Each domain snapshots its state before every step:
  instant tracing, but it copies all state on every step of every run. (c) Trace against the
  halted state only: free, but by then the inputs are usually NaN already and the trace
  blames nothing. **Decided 2026-11-03: (a), replay to N−1.**
- **R1.** Bit identity depends on each lane arm being the exact scalar expression. A future
  op added to `apply` but not to `eval_batch` would break it silently. Mitigation: both get
  their arms from one macro, and the property test generates every `Op` variant.
- **R2.** The speedup may be small if the cost is in the neighbour iteration rather than
  dispatch. The benchmark decides, and the roadmap reports the number honestly, whatever it
  is (§21.1, §23.1).
- **R3.** Benchmarks swing a lot when a game is running. Measure on an idle machine, take
  the median of three, and don't record a figure taken with the crew bench guard overridden.

## 7. Validation

- **Bit-identity property test (lattice-expr).** Random programs of 1–200 ops covering every
  `Op` variant, with inputs drawn to include ±0.0, ±∞, NaN, subnormals and values near
  overflow. Every `active` from 1 to `LANES`. Compare `eval_batch` to `eval` lane by lane
  with `to_bits()` equality, NaN included where the scalar result is NaN (compare `is_nan`
  for both, since Rust doesn't pin NaN payloads). Deterministic seeded RNG and at least
  10,000 programs.
- **Domain identity.** The existing `laws` validation cases (LJ bit-identical to the
  built-in, 0 of 400 values differing, and thread-count identity on 1, 2, 3 and 8 threads)
  must pass unchanged on the batched path. Add a case where the particle count is not a
  multiple of `LANES` and a member-dependent truncated potential is used.
- **Origins.** Unit tests that CSE keeps the first origin, folding keeps the source
  expression's origin, derivative ops inherit, and `fingerprint`/`==` ignore origins.
- **Tracing.** One fixture per kind: a pair potential dividing by `r - 1` with atoms placed
  at distance 1; a body force with `ln(px)` at a negative position; a rate law with
  `1 / c(A)` as A runs out. Each asserts `E0950`, the span's exact byte range, and the
  operands. Plus one test where the NaN comes from the initial state, which must blame the
  input and no op.
- **Inspect.** A snapshot test of `lattice inspect expr examples/damped_spring.lattice`, and
  error tests for an unknown law and a file that doesn't compile.
- **Benchmark.** `lattice bench particles-lj-expr` at 1,024 and 16,384 atoms, scalar path
  against batched path, with the existing correctness checks passing. Acceptance: batched is
  faster than scalar at both sizes, and the ratio to the built-in is recorded in the
  roadmap. There is no target ratio, because the honest number is the deliverable.
- `cargo test --workspace --all-features` and clippy with `-D warnings` stay clean.
  `lattice validate` (with `--features gpu`) passes.
